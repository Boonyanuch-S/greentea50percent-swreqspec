# แผนฟีเจอร์เข้าสู่ระบบ (Login)

อ้างอิง: `specs/009-เข้าสู่ระบบ/spec.md`  
Spec ID: `SPEC-AUTH-009` | สถานะของ spec: `Draft v2`

## 1. สรุปแนวทาง

1. สร้างหน้า login สำหรับผู้ใช้ 4 บทบาทตาม `ASM-01` และรองรับการเปิดระบบครั้งแรกตาม `FR-AUTH-01`
2. รับ username และ password แล้วส่งตรวจสอบผ่าน Login API ตาม `FR-AUTH-02`, `FR-AUTH-03`
3. เมื่อสำเร็จ เก็บ Token ที่มีอายุ 30 นาทีและนำผู้ใช้ไปหน้าหลักตามบทบาทตาม `FR-AUTH-04`, `IF-TOKEN-01`, `ASM-02`, `ASM-03`
4. แยกข้อความกรณีข้อมูลรับรองไม่ถูกต้องออกจากกรณี Login API ขัดข้องตาม `FR-AUTH-05`, `SEC-AUTHMSG-01`, `ASM-04`
5. ตรวจสอบ Token ก่อนเข้าฟังก์ชัน และเมื่อหมดอายุให้แจ้งเตือนแล้วกลับหน้า login ตาม `FR-AUTH-01`, `AC-AUTH-04`

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) สำหรับหน้าบ้าน | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างหน้า login และการนำทางตามบทบาท รองรับ `FR-AUTH-01`, `FR-AUTH-02`, `FR-AUTH-04` |
| Python FastAPI สำหรับหลังบ้าน | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ทำ Login API และตรวจสอบ Token รองรับ `FR-AUTH-03`, `FR-AUTH-05` |
| ระบบจัดเก็บ Token ฝั่ง client ตามอายุที่กำหนด | `IF-TOKEN-01`, `ASM-02` | รายละเอียดกลไกจัดเก็บยังต้องสอดคล้องกับการตัดสินใจเรื่อง session ใน `Q-06` |
| ระบบยืนยันตัวตนและแหล่งข้อมูลบัญชีผู้ใช้เดิม | `FR-AUTH-03` | การสร้างบัญชีใหม่อยู่นอกขอบเขตตาม Scope |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับข้อกำหนด |
|---|---|---|
| UserAccount | `user_id`, `username`, `password_verification_reference`, `role` | `FR-AUTH-02`, `FR-AUTH-03`, `FR-AUTH-04`, `ASM-01` |
| AuthToken | `token_id`, `user_id`, `issued_at`, `expires_at`, `role` | `FR-AUTH-04`, `IF-TOKEN-01`, `DOM-PDPA-02`, `ASM-02` |
| RoleHomeRoute | `role`, `home_route` | `FR-AUTH-04`, `ASM-03`; ค่าเส้นทางของแต่ละบทบาทยังรอคำตอบ `Q-01` |
| LoginErrorResponse | `error_type`, `message` | `FR-AUTH-03`, `FR-AUTH-05`, `SEC-AUTHMSG-01`, `ASM-04` |

ไม่เพิ่มฟิลด์สำหรับการสร้างบัญชีใหม่หรือการรีเซ็ตรหัสผ่าน เพราะอยู่นอกขอบเขตตาม Scope และยังไม่เพิ่มฟิลด์สำหรับ remember me, refresh token, multi-device หรือ multi-session จนกว่าจะได้คำตอบ `Q-06`.

## 4. API / หน้าจอ

| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| `GET /login` | Input: สถานะการมี Token; Output: หน้า login เมื่อเปิดระบบครั้งแรกหรือไม่มี Token ที่ใช้งานได้ | `FR-AUTH-01`, `FR-AUTH-02` |
| `POST /api/login` | Input: `username`, `password`; Output: Token, วันหมดอายุ และบทบาทเมื่อสำเร็จ หรือข้อความทั่วไปเมื่อข้อมูลรับรองไม่ถูกต้อง | `FR-AUTH-03`, `FR-AUTH-04`, `FR-AUTH-05`, `IF-TOKEN-01`, `SEC-AUTHMSG-01` |
| `GET /api/auth/me` | Input: Token; Output: ผู้ใช้และบทบาทที่ผ่านการยืนยัน หรือผล Token หมดอายุ/ใช้ไม่ได้ | `DOM-PDPA-02`, `FR-AUTH-04`, `IF-TOKEN-01`, `NFR-SEC-02`; การจัดการ Token ไม่ถูกต้องยังรอ `Q-03` |
| `GET /home/{role}` | Input: บทบาทจาก Token; Output: หน้าหลักของบทบาทนั้น | `FR-AUTH-04`, `AC-AUTH-01`, `ASM-03`; ชื่อหรือเส้นทางจริงยังรอ `Q-01` |
| ตัวตรวจสอบ Token ก่อนเรียกฟังก์ชัน | Input: Token จาก session; Output: อนุญาตให้ทำงาน หรือแสดงหน้าต่างแจ้งเตือนแล้วนำไป `GET /login` เมื่อหมดอายุ | `FR-AUTH-01`, `AC-AUTH-04`, `IF-TOKEN-01`, `ASM-02` |

การแจ้งเตือนแบบ in-app ตามบทบาทไม่อยู่ในแผนนี้ตาม Out of scope; ฟีเจอร์นี้ส่งต่อบทบาทหลัง login สำเร็จเท่านั้นจนกว่าจะตอบ `Q-04` ตาม `NFR-SEC-02`.

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `DOM-PDPA-02` | `AuthToken`, `GET /api/auth/me` และตัวตรวจสอบ Token ใช้บทบาทจำกัดการเข้าถึงข้อมูลนักศึกษา | ใช้แล้ว |
| `SEC-AUTHMSG-01` | `POST /api/login` ส่งข้อความเดียวกันเมื่อ username หรือ password ไม่ถูกต้อง และไม่เปิดเผยสาเหตุ | ใช้แล้ว |
| `IF-TOKEN-01` | `AuthToken` มี `expires_at`, Login API ออก Token และตัวตรวจสอบ Token บังคับกลับหน้า login เมื่อหมดอายุ | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-AUTH-01` | `test_AC_AUTH_01_login_success_routes_by_role` | ใช้บัญชีและรหัสผ่านที่ถูกต้อง ตรวจว่าได้รับ Token ที่มีวันหมดอายุและถูกนำไปหน้าหลักของบทบาทที่กำหนด โดยรายละเอียดเส้นทางจริงยังรอ `Q-01` |
| `AC-AUTH-02` | `test_AC_AUTH_02_wrong_password_uses_generic_message` | ใช้ username ที่มีอยู่แต่ password ผิด ตรวจว่า login ไม่สำเร็จและแสดงข้อความ `บัญชีหรือรหัสผ่านไม่ถูกต้อง` |
| `AC-AUTH-03` | `test_AC_AUTH_03_unknown_username_uses_same_generic_message` | ใช้ username ที่ไม่มีอยู่ ตรวจว่าข้อความเหมือน `AC-AUTH-02` และไม่เปิดเผยว่าบัญชีไม่มีอยู่จริง |
| `AC-AUTH-04` | `test_AC_AUTH_04_expired_token_redirects_immediately` | ใช้ Token ที่หมดอายุระหว่าง session แล้วเรียกฟังก์ชัน ตรวจว่ามีหน้าต่างแจ้งเตือนและกลับหน้า login ทันที โดยใช้อายุ 30 นาทีตาม `ASM-02` |

กรณี Login API ไม่ตอบสนองตาม `ASM-04` ยังไม่มี AC เฉพาะใน spec จึงวางไว้เป็นพฤติกรรมของ `FR-AUTH-03` และต้องเพิ่มการทดสอบเมื่อทีมกำหนด AC ที่เกี่ยวข้องโดยไม่สร้าง ID ใหม่เอง.

## 7. ลำดับงาน

1. กำหนด contract ของ Login API, รูปแบบ Token และ `expires_at` ตาม `FR-AUTH-03`, `FR-AUTH-04`, `IF-TOKEN-01`, `ASM-02`
2. เชื่อมต่อแหล่งข้อมูลบัญชีผู้ใช้เดิมและอ่านบทบาทตาม `FR-AUTH-03`, `ASM-01` โดยไม่สร้างบัญชีใหม่ตาม Scope
3. สร้างหน้า login และ input สำหรับ username/password ตาม `FR-AUTH-01`, `FR-AUTH-02`
4. สร้างการแยกผลลัพธ์ login สำเร็จ, ข้อมูลรับรองไม่ถูกต้อง และ Login API ขัดข้องตาม `FR-AUTH-03`, `FR-AUTH-05`, `SEC-AUTHMSG-01`, `ASM-04`
5. สร้างการออกและตรวจสอบ Token พร้อมอายุ 30 นาทีตาม `FR-AUTH-04`, `IF-TOKEN-01`, `ASM-02`
6. สร้างการนำทางไปหน้าหลักตามบทบาทและส่งต่อ role ให้ส่วนที่เกี่ยวข้องตาม `FR-AUTH-04`, `ASM-03`, `NFR-SEC-02`
7. เพิ่มตัวตรวจสอบ Token ที่แสดงหน้าต่างแจ้งเตือนและกลับหน้า login เมื่อหมดอายุตาม `FR-AUTH-01`, `AC-AUTH-04`
8. ทดสอบตาม `AC-AUTH-01` ถึง `AC-AUTH-04` และตรวจการไม่เปิดเผยข้อมูลบัญชีตาม `AC-AUTH-02`, `AC-AUTH-03`, `SEC-AUTHMSG-01`
9. ทบทวนรายละเอียดที่ขึ้นกับ `Q-01` ถึง `Q-06` ก่อนสร้างส่วนที่เกี่ยวข้องกับเส้นทางหน้าหลัก, Token ที่ใช้ไม่ได้, การแจ้งเตือน, การล็อกบัญชี และ session policy

## 8. สิ่งที่ยังไม่ทำ

- `Q-01` ต้องกำหนดชื่อหรือเส้นทางหน้าหลักของกรรมการสโมสร เจ้าหน้าที่คณะ อาจารย์ที่ปรึกษา และเจ้าหน้าที่กองกิจอย่างไร? เกี่ยวกับ `FR-AUTH-04`, `AC-AUTH-01`  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-02` เมื่อเปิดระบบครั้งแรกโดยยังไม่มี Token ต้องแสดงหน้า login ทันทีหรือมีหน้าต่างแจ้งเตือนร่วมด้วย? เกี่ยวกับ `FR-AUTH-01`  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-03` Token ไม่ถูกต้องหรือถูกยกเลิก ต้องจัดการเหมือน Token หมดอายุหรือไม่? เกี่ยวกับ `IF-TOKEN-01`, `FR-AUTH-01`, `AC-AUTH-04`  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-04` `NFR-SEC-02` เป็นข้อกำหนดของฟีเจอร์ login โดยตรง หรือให้ฟีเจอร์การแจ้งเตือนเป็นผู้รับผิดชอบ โดย login เพียงส่งต่อบทบาท? เกี่ยวกับ `NFR-SEC-02`  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-05` ต้องจำกัดจำนวนครั้งที่กรอกรหัสผ่านผิดหรือล็อกบัญชีชั่วคราวหรือไม่? เกี่ยวกับ Q-02 เดิม  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-06` อนุญาตให้บัญชีเดียวกัน login หลายอุปกรณ์หรือหลาย session พร้อมกันหรือไม่ และต้องรองรับ remember me หรือ refresh token หรือไม่? เกี่ยวกับ Q-04 และ Q-05 เดิม  
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
