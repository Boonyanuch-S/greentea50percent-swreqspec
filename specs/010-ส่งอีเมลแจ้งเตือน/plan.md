# แผนทางเทคนิค: ส่งอีเมลแจ้งเตือน

## 1. สรุปแนวทาง
ฟีเจอร์นี้รับคำขอแจ้งเตือนจาก use case อื่นผ่าน internal call ตาม `IF-CALL-01` (`FR-NOTI-01`).
ระบบจะเลือก template ตามประเภทเหตุการณ์และสร้างเนื้อหาอีเมล (`FR-NOTI-02`).
ระบบจะส่งอีเมลผ่านบริการอีเมลภายนอกตาม `IF-EMAIL-01` (`FR-NOTI-03`).
ทุกความพยายามส่งจะถูกบันทึกผล และความล้มเหลวจะถูกส่งเข้าคิว retry (`FR-NOTI-04`, `FR-NOTI-05`, `NFR-REL-01`).
ไม่มีหน้าจอผู้ใช้ของฟีเจอร์นี้ เพราะเป็น service ภายในที่ use case อื่นเรียกใช้ (`IF-CALL-01`).

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| Python FastAPI สำหรับ internal service | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้รับคำขอจาก use case ต้นทางตาม `IF-CALL-01`; ยังไม่กำหนดรายละเอียดการยืนยันตัวตนเพราะ spec ไม่ได้ระบุ |
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ฟีเจอร์นี้ไม่มีหน้าจอผู้ใช้ตาม `IF-CALL-01` จึงยังไม่สร้างหน้าจอ React |
| บริการอีเมลภายนอก เช่น Amazon SES | `IF-EMAIL-01` | ต้องรอยืนยันบริการจริงและ contract ที่เกี่ยวข้องกับ `Q-04` |
| กลไกคิวและ worker สำหรับ retry | `NFR-REL-01`, `FR-NOTI-05` | จำนวนครั้งและช่วงเวลา retry ยังไม่กำหนดตาม `Q-01` จึงยังไม่เลือกผลิตภัณฑ์หรือค่าคอนฟิกเฉพาะ |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| NotificationRequest | รหัสคำขอ, ประเภทเหตุการณ์, ผู้รับ, ข้อมูลสำหรับสร้างเนื้อหา, สถานะคำขอ | `FR-NOTI-01`, `FR-NOTI-02`, `FR-NOTI-03` |
| EmailDeliveryAttempt | รหัสคำขอ, ลำดับความพยายาม, เวลาเริ่ม/สิ้นสุด, ผลการส่ง, รายละเอียดข้อผิดพลาด | `FR-NOTI-04`, `AC-NOTI-04` |
| NotificationRetryQueueItem | รหัสคำขอ, สถานะคิว, เวลาที่กำหนดให้ลองครั้งถัดไป, จำนวนครั้งที่ลองแล้ว | `FR-NOTI-05`, `NFR-REL-01`, `AC-NOTI-02` |
| EventEmailTemplate | ประเภทเหตุการณ์, เนื้อหา template, ตัวแปรที่รองรับ, เวอร์ชัน | `FR-NOTI-02`, `AC-NOTI-03` |

รายละเอียดรายการเหตุการณ์ทั้ง 10 กรณี แหล่งที่มา/เจ้าของ template และโครงสร้างข้อมูลจริงยังไม่กำหนด จึงยังไม่ล็อก schema เพิ่มเติมจนกว่าจะตอบ `Q-03` และ `Q-04`.

## 4. API / หน้าจอ

| รายการ | Input หลัก | Output หลัก | รองรับ |
|---|---|---|---|
| `POST /internal/notifications/email` | ประเภทเหตุการณ์, ผู้รับ, ข้อมูลสำหรับ template, รหัสเหตุการณ์ต้นทาง | รหัสคำขอแจ้งเตือนและสถานะรับคำขอ | `FR-NOTI-01`, `IF-CALL-01` |
| `POST /internal/notifications/email/{request_id}/attempt` | รหัสคำขอแจ้งเตือน | ผลการส่งจากบริการอีเมลภายนอก | `FR-NOTI-03`, `IF-EMAIL-01` |
| Retry worker สำหรับรายการในคิว | รายการคิวที่ถึงเวลาลองซ้ำ | ผลการลองส่งและการอัปเดตสถานะคิว | `FR-NOTI-05`, `NFR-REL-01` |
| หน้าจอผู้ใช้ของฟีเจอร์นี้ | ไม่มี | ไม่มี | `IF-CALL-01` ระบุว่าไม่มีหน้าจอของตัวเอง |

ชื่อ path, รูปแบบ error response, วิธีเรียกบริการอีเมลจริง และนโยบาย retry ยังต้องยืนยันตาม `Q-01`, `Q-03` และ `Q-04`.

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `IF-EMAIL-01` | การส่งผ่านบริการอีเมลภายนอกในหัวข้อ 2, API การส่งในหัวข้อ 4 และ test `AC-NOTI-01` | ใช้แล้ว |
| `IF-CALL-01` | Internal API และการไม่สร้างหน้าจอในหัวข้อ 2 และ 4 | ใช้แล้ว |
| `NFR-REL-01` | `NotificationRetryQueueItem`, retry worker และ test `AC-NOTI-02` | ใช้แล้ว แต่รายละเอียดจำนวนครั้ง/ช่วงเวลายังรอ `Q-01` |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-NOTI-01` | `test_AC_NOTI_01_send_email_within_required_time` | เรียก internal service ด้วยเหตุการณ์และผู้รับที่มีอีเมลถูกต้อง ใช้ email provider stub ตรวจว่ามีการส่งถึงผู้รับและตรวจเวลาตาม SLA; ยังทดสอบเต็มรูปแบบไม่ได้จนกว่าจะตอบ `Q-02` |
| `AC-NOTI-02` | `test_AC_NOTI_02_retry_without_failing_source_event` | จำลอง temporary failure จาก email provider ตรวจว่าคำขอถูกใส่คิว retry และผลลัพธ์ของเหตุการณ์ต้นทางไม่ล้มเหลว; จำนวนครั้ง/ช่วงเวลายังรอ `Q-01` |
| `AC-NOTI-03` | `test_AC_NOTI_03_render_event_template` | ส่งคำขอของประเภทเหตุการณ์ที่กำหนด ตรวจว่าเนื้อหาและตัวแปรที่ render ตรงกับ template ของประเภทนั้น; รายการ 10 กรณียังรอ `Q-03` |
| `AC-NOTI-04` | `test_AC_NOTI_04_log_every_delivery_attempt` | จำลองทั้งการส่งสำเร็จและไม่สำเร็จ ตรวจว่ามี log ผลการส่งสำหรับทุกความพยายาม; รูปแบบข้อมูล log ยังต้องยืนยันเพิ่มเติม |

## 7. ลำดับงาน

1. ยืนยันรายการเหตุการณ์ 10 กรณีและ template ของแต่ละกรณี (`FR-NOTI-02`, `AC-NOTI-03`, `Q-03`).
2. กำหนด contract ของ internal request และข้อมูลผู้รับ (`FR-NOTI-01`, `IF-CALL-01`, `Q-04`).
3. ออกแบบข้อมูลคำขอ template, ความพยายามส่ง, log และรายการ retry (`FR-NOTI-01` ถึง `FR-NOTI-05`, `NFR-REL-01`).
4. กำหนด contract และผลลัพธ์ข้อผิดพลาดของบริการอีเมลภายนอก (`IF-EMAIL-01`, `FR-NOTI-03`, `Q-04`).
5. ออกแบบการสร้างเนื้อหาและส่งอีเมลตามประเภทเหตุการณ์ (`FR-NOTI-02`, `FR-NOTI-03`).
6. ออกแบบการบันทึกผลทุกความพยายามส่ง (`FR-NOTI-04`, `AC-NOTI-04`).
7. ออกแบบการแยก temporary failure และการเข้าคิว retry โดยไม่ทำให้เหตุการณ์ต้นทางล้มเหลว (`FR-NOTI-05`, `NFR-REL-01`, `AC-NOTI-02`, `Q-01`).
8. เขียน automated tests ตาม `AC-NOTI-01` ถึง `AC-NOTI-04` ด้วย email provider stub และข้อมูลเหตุการณ์จำลอง.

## 8. สิ่งที่ยังไม่ทำ

- `Q-01` "ตามที่กำหนดไว้ใน Infrastructure Requirements" (NFR-REL) หมายถึงเอกสารข้อกำหนดชุดใด และมีตัวเลขจำนวนครั้ง/ช่วงเวลาส่งซ้ำเท่าไร? ส่วน retry policy และการตั้งค่าที่เกี่ยวข้องจะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-02` "เวลาที่กำหนด" ใน AC-NOTI-01 ไม่มีตัวเลขระบุ ต้องการ SLA ที่ชัดเจน ส่วนการตรวจสอบเวลาส่งตาม SLA จะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-03` Trigger ระบุว่ามี 10 กรณี แต่มีตัวอย่างเพียง 2 กรณี ต้องการรายการครบทั้ง 10 กรณีและ template ของแต่ละกรณี ส่วน mapping เหตุการณ์และ template ที่ยังไม่ครบจะยังไม่สร้างจนกว่าจะได้คำตอบ
- `Q-04` ขอภาพต้นฉบับที่ชัดกว่านี้ของแถว Stakeholder & Interest เพื่อยืนยันถ้อยคำที่แน่นอน ส่วนการปรับรายละเอียด stakeholder และผลกระทบต่อเนื้อหาแจ้งเตือนจะยังไม่สร้างจนกว่าจะได้คำตอบ
